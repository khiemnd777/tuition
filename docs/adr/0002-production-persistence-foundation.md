# ADR 0002: Production Persistence Foundation

Date: 2026-05-23

## Status

Accepted

## Context

The original DEKISUGI app stores payment rows in request payloads and local email config files. The production roadmap needs durable modules for students, invoices, payments, reconciliation, notifications, reports, and audit logs. Those modules need one consistent persistence boundary before business tables are added.

## Decision

- PostgreSQL is the production database target.
- Schema changes are applied through embedded SQL migrations under `migrations/`.
- `go run . migrate up` applies pending migrations and records checksums in `schema_migrations`.
- `go run . migrate status` reports applied, pending, or checksum-drifted migrations.
- Database URLs are supplied by environment variables only:
  - `DEKISUGI_DATABASE_URL_LOCAL`
  - `DEKISUGI_DATABASE_URL_STAGING`
  - `DEKISUGI_DATABASE_URL_PRODUCTION`
  - fallback: `DEKISUGI_DATABASE_URL`, then `DATABASE_URL`
- The active environment is `DEKISUGI_ENV` or `APP_ENV`, normalized to `local`, `staging`, or `production`.
- Production table primary keys use PostgreSQL `uuid` values generated by `gen_random_uuid()`.
- Mutable operational tables include `created_at`, `updated_at`, `created_by_user_id`, and `updated_by_user_id` when actor attribution is useful.
- Audit log entries are append-only at the database layer.

## Consequences

- Current QR and email flows continue to run without a database unless a DB command is invoked.
- Future modules can depend on a stable UUID and timestamp convention.
- Secrets stay outside tracked files.
- Production backup and restore procedures must use PostgreSQL-native tooling and run migrations after restore.
